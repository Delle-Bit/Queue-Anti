## Project

Medical clinic queue management system: customers join queues or book appointments, staff call tickets across stations (front desk → laboratory(s) → doctor), with live status updates, priority queuing (Senior/PWD/Pregnant), analytics, and AI-assisted features.

**Stack**: Node.js + Express 5 + Socket.IO, MySQL (`mysql2`, schema auto-created on boot), static HTML/CSS/JS in `public/` (no frontend framework/bundler), JWT auth (8h expiry, role-based).

## Commands

```bash
npm install       # install dependencies
npm start          # run the server (default port 3000; requires local MySQL on 3306)
npm test           # syntax-check every backend file via `node --check`, then run verify_gemini_keys.js (no test framework in this repo)

docker compose up --build   # the app plus its own MySQL, no local Node or MySQL needed
```

There is no linter. `npm test` verifies every backend file parses and runs the one real assertion suite in the repo, `verify_gemini_keys.js` (30 offline checks over Gemini key rotation — it stubs axios and the pool, so it needs no key, no network and no database). Everything else is still manual: exercise the routes and pages after changes.

Setup requires a local MySQL server and a `.env` with `PORT`, `JWT_SECRET`, and optional `GEMINI_API_KEY` / `API_ALLAROUND` / `NVIDIA_API_KEY` - or Docker, which brings its own MySQL (`Dockerfile`, `docker-compose.yml`, and [DOCKER.md](DOCKER.md) for the reasoning). `dotenv.config()` runs *before* every local require in `server.js` and must stay there: `config.js` and `database.js` both read `process.env` at module scope, and when it ran after them the `JWT_SECRET` from `.env` was silently ignored in favour of the hardcoded development default. The first server run auto-creates the `clinic_v2` database, all tables, seed accounts, seed labs/doctors, and default service packages — no manual migrations. Seed accounts are documented in [README.md](README.md).

## Architecture

**Request flow**: `server.js` is the sole entry point — it wires Express middleware, mounts routers under `/api/*`, defines the QR check-in endpoints and the socket.io instance, then seeds the DB and starts listening. Route order matters (`server.js` comments call this out): `/api/auth` and `/api/packages` are public/self-guarded, `/api/queue` and `/api/assistant` require only `authenticateToken`, `/api/reports` additionally requires the `owner` role, and `/api/admin` plus the catch-all `/api` (both pointing at `routes/admin.js`) require `requireAdmin`. `/api/display` is mounted **before** the authenticated routers because it is public — it feeds a wall-mounted screen with nobody signed in to it — and `/api/walkin` sits with the other operational routers, doing its own role check inside. Every authenticated router additionally passes through `enforceIdleTimeout` (`session_activity.js`), which rejects a staff token that has gone 15 minutes without reported activity.

**Routers** (`routes/`), each a thin Express router pulling `{ pool }` from `database.js` directly:
- `auth.js` — login/register, ID-image upload + OCR-assisted verification, pending-registration approval
- `queue.js` — queue join/`next`/`complete-step`, `finalize` (front-desk-only close-out), `call-back` (undo the last advance), `reinsert` (front-desk line cutting), `hold`/`resume`, ticket status, `buildCustomerStatus()` (customer-facing state used by the assistant too)
- `admin.js` — staff/labs/doctors CRUD, analytics, searchable audit log and archives; exports `STAFF_ROLES`/`ADMIN_ROLES` guard sets consumed by `server.js` route mounting
- `packages.js` — service package catalog, searchable by ID/name/category; `DELETE` archives a package. A package may name the `test_structure_id` its laboratory step expects
- `test_structures.js` — the result form for each kind of test. Reads are open to any staff member (the laboratory renders its form from them), writes are administrator-only and carry a reason
- `walkin.js` — phone-less walk-in intake: registers the patient at the counter, queues them, lists them, and serves the data for their two printed forms
- `display.js` — the lobby queue board's data. The **only** queue endpoint with no authenticated caller behind it, and therefore the only one that must never answer with a patient's name
- `reports.js` — owner-only reporting
- `assistant.js` — the "VA" (virtual assistant) backend; calls into `queue.js`'s `buildCustomerStatus()` and `ai_services.js`

**Auth & roles** (`config.js`): `JWT_SECRET`, and two role-guard middlewares — `requireStaff` (any of `STAFF_ROLES`) and `requireAdmin` (any of `ADMIN_ROLES` = admin/admintechnical/owner). `server.js` defines its own `authenticateToken`/`verifyRoles` inline rather than importing from `config.js`. Roles: `customer`, `frontdesk`, `laboratory`, `doctor`, `admin`, `admintechnical`, `owner` — see [README.md](README.md) for what each can access.

**Starting a visit** (`queue_start.js`): `startPackageQueue()` is the one place a visit enters the queue, whichever door the patient came through — a customer joining from their own phone (`POST /api/queue/start-package`), an appointment being checked in (`startQueueFromAppointment` in `server.js`), or the front desk booking in a phone-less walk-in (`POST /api/walkin`). It writes the `queue_sequences` row, mints the ticket, opens the step-0 `queue` row and the `queue_logs` timing record, and reports back one of `{ alreadyActive }`, `{ unavailable }` or the started visit.

It exists because there were already two copies of those six statements and they had drifted: the appointment copy re-derived the step count by hand and was left one step short the moment the closing front desk step was added. `getPackageSteps()` lives here too, for the same reason — it is the routing table a queue row's `step_index` indexes into, so every caller has to build it identically. The only per-caller difference left is `rowId`, because the appointment path has always named its step-0 row `appt_<id>_<seq>` while the others use `cust_<id>_<seq>`; from step 1 on, `/complete-step` derives every id from `stepRowId()` regardless.

**Queue engine** (`queue_automation.js`): priority scoring (`calculateScore` — Senior/PWD/Pregnant get a weighted head start, plus 1 point per minute waited) and atomic per-day-per-station ticket numbering (`nextTicketNumber`, backed by the `ticket_counters` table with `ON DUPLICATE KEY UPDATE` to stay race-safe under concurrent check-ins). `peekTicketNumber` is a non-mutating lookahead used for previews.

`composeServiceSteps` is the single definition of the shape of a visit, and **every route is front-desk-to-front-desk**: it prepends `FRONT_DESK_STEP` (the cashier) and appends `FRONT_DESK_FINAL_STEP` (the gatekeeper) around the stations stored in `package_laboratories`. Neither bookend is a stored station row, so `hasServiceStations(steps)` — not `steps.length` — is what answers "does this package do anything?". Each queue row carries a `step_index` that indexes straight into that list, which is how `/complete-step` routes and how `/finalize` recognises the closing step.

`orderWaitingList` produces a station's waiting list *in the order it will actually be called* — priority scoring for ordinary rows, and for a re-inserted row, the position named by its `reinsert_after` (the queue id it must be called immediately after). Anchoring to a neighbour rather than storing a rank is deliberate: a stored rank re-applies itself as the line drains, so a patient placed "second" stays second forever and their turn never arrives.

**Re-insertion has two shapes** (`POST /api/queue/reinsert`, front desk only). Without `target_step_index` it holds a patient's place in the line they are already in. With one, the desk routes them back to an *earlier step of their own service* — the case where somebody reaches the closing front desk step with a laboratory result missing. That path abandons the row they are standing at (`cancelled`, and its open `queue_logs` row is closed off), re-opens the target step's row at slot 2 of that station's line, rolls `queue_sequences.current_step` back, and logs a fresh attempt at that station. It is backwards-only: skipping a patient *forward* would roll the sequence counter over stations they never attended, so it is refused with a message pointing at the station's own "Done" button. `GET /api/queue/reinsert-candidates` carries each patient's own route with a `selectable` flag per step, which is what lets the picker offer only the steps on their availed service.

Because a patient can be sent back, **a step may be walked more than once**: queue row ids are derived from the step (`stepRowId`), so `/complete-step` upserts the next row rather than inserting it. A plain insert collided on the primary key and stranded the patient at the step they were sent back to.

Appointment-to-queue promotion (`startQueueFromAppointment` in `server.js`) derives `total_steps` from `composeServiceSteps` rather than re-deriving the arithmetic, and writes a `queue_sequences` row tracking `current_step`/`total_steps` plus the outcome fields the front desk fills in at the end.

**Phone-less walk-in intake** (`routes/walkin.js`): this clinic's queue is phone-first — a customer registers on their own device, picks a service, joins from it, and watches their place in the line on it. A patient who arrives without a phone can do none of that, and before this could not be queued at all. So the front desk does it for them, and what the patient gets instead of a phone is paper.

A walk-in is **an ordinary `users` row flagged `is_walk_in`, not a parallel queue**. That is the load-bearing decision: `queue_sequences.customer_id` is a `NOT NULL` foreign key into `users`, and priority scoring, ticket minting, `/complete-step` routing, re-insertion, hold/resume, finalisation, the station dashboards, the patient file panel and the medical record all key off it. A separate walk-in table would mean a second implementation of every one of those, and the two would drift. The cost of the decision is that an account exists which nobody chose a password for, so it must not be signable-in to: `routes/auth.js` refuses `is_walk_in` accounts before the hash compare, the stored hash is of 32 random bytes nobody holds, and password reset never fires because these rows have no email.

`queue_sequences.intake_channel` (`online` / `appointment` / `walkin`) records which door a visit came through; the queue engine treats all three identically. `paid_at` is stamped when the front desk clears the opening (cashier) step — on every visit, not just appointments — because the Diagnosis Form is printed off the back of it and it cannot be inferred from the step counter: a patient sent back to an earlier step rolls `current_step` backwards and has still paid.

**Printed clinic documents** (`public/clinic-pdf.js`, `public/walkin-forms.js`): the shared jsPDF letterhead, and the two walk-in forms built on it. `clinic-pdf.js` was extracted out of `customer.js`, where it had been written for the medical-record export as the only thing that printed — a clinic's paperwork has to look like one clinic's paperwork, and a second letterhead written alongside the first is how two documents from the same desk end up with different margins and a different footer. It also holds the fill-in primitives a form completed *by hand* needs (`pdfBlankGrid` prints a rule to write on where the record would print an em dash, plus `pdfRuledLines`, `pdfCheckboxes`, `pdfSignature`, `pdfNumberPanel`) and `pdfFlow`, a page-flowing cursor every block asks for room from before it draws.

The **Intake Form** prints on queue creation, carrying the queue number the patient will be called by, the service availed, and the medical questions a customer would otherwise answer in the app. Its checklist is the `.req-ch-checkbox` list from `customer.html` **verbatim**, and the five yes/no questions are the `pc-*` selects — that is what makes the desk's later transcription a copy rather than a translation. The **Diagnosis Form** prints after payment and is shaped by the service: the station route becomes a sign-off table, and the service's own `test_structure` becomes the results section — a `structured` form prints its parameters with units and reference ranges to write into, a `freeform` one prints ruled space for a written report.

**Public queue display and announcements** (`public/display.html`, `routes/display.js`): the lobby board. Three parties, deliberately: the front desk or an admin *performs* the call, the server *broadcasts* it, and the board — the thing with speakers in the room — chimes and speaks it. `queueAnnounce` is emitted only from `POST /api/queue/next` and `/call-back`, never from the general `queueUpdate` that fires on every mutation; a board that spoke on those would talk over itself continuously. The chime is synthesised through WebAudio (no asset to ship or fail) and the announcement read by `speechSynthesis`, with the ticket expanded digit by digit ("Q, 0, 0, 4") because a speech engine reads `Q-004` as "Q minus four" and drops the very digits printed on the patient's ticket. Audio needs a user gesture before a browser will allow it, so the board has an explicit **Enable sound** button rather than appearing to work and staying silent.

**Audit trail** (`audit.js`): `recordAudit({ req, action, entityType, entityId, summary, before, after, reason })` writes one `audit_logs` row answering What / Who / When / Why, with scrubbed before+after snapshots and a `details` diff of only the fields that moved. `requireReason` is the Express guard that makes the Why mandatory — configuration endpoints reject the request rather than record a blank reason. `recordAudit` never throws: a failed audit write must not roll back a change the clinic has already made.

**Soft delete** (`archive.js`): `archiveRecord(table, idColumn, id, entityType, req, reason)` flags the row `archived`, files a scrubbed snapshot plus a human-readable `label` under `archived_records`, and audits the change. `ARCHIVE_TABLE_MAP` is the single map from `entity_type` back to its table, shared by restore and permanent-delete so the two cannot drift apart. It lives outside `routes/admin.js` because `routes/packages.js` archives through it too.

**Medical test structures** (`routes/test_structures.js`, tables `test_structures` / `test_structure_fields`): the result form for a kind of test — which parameters the laboratory types in, each one's unit, reference range, input type (`number`/`text`/`select`) and default. These were a hardcoded `testTemplates` object inside `public/laboratory.js`, so correcting a reference range needed a developer; they are administrator-owned data now, seeded once from the old hardcoded set by `seedTestStructures()` in `server.js` and never re-applied on later boots. `input_mode` is the fork: `structured` renders the parameter grid, `freeform` renders the rich text notepad instead and stores no fields. A `service_packages.test_structure_id` names the form a service expects, and the laboratory workspace opens on it (the id rides along on `GET /api/queue/station`); staff can still pick another form for an individual visit.

**Rich text** (`rich_text.js`): `sanitizeRichText` / `richTextToPlain` for the freeform notepad. This is the one place where one user's input is shown to another as markup rather than text — a laboratory writes the note, the patient reads it on their medical history — so it is sanitised on write in `POST /api/clinical-records`, which is the boundary. Strict allow-list: an allowed tag is re-emitted with **every attribute dropped**, anything else is removed while its text is kept, and `<script>`-style elements go with their content. `notes` keeps a flattened plain-text copy alongside `data.rich_notes` so the PDF export, the AI summaries and the assistant keep working unchanged. `sanitizeRichHtml` in `shared.js` mirrors it for rendering; the client copy is a convenience, not the boundary.

**Staff session timeout** (`session_activity.js`): the 15-minute inactivity rule, in two halves. The browser owns the clock (only it sees mouse/keyboard) and reports real activity via `POST /api/session/heartbeat`; the server owns the verdict and rejects a stale token with `401` + an `X-Session-Timeout` header. Deliberately heartbeat-driven rather than traffic-driven — the staff dashboards poll their queue every 5 seconds, so "time since last request" would never expire on an unattended screen.

**Database** (`database.js`): single `pool` (mysql2) exported alongside `initDB()` and `DEFAULT_SERVICES`. `initDB()` creates ~20 tables (`users`, `queue`, `queue_sequences`, `queue_logs`, `appointments`, `medical_records`, `clinical_records`, `lab_notes`, `pricing_faqs`, `ticket_counters`, `ai_settings`, `ai_logs`, `pending_registrations`, `audit_logs`, etc.) and uses `addColumnIfMissing`/`addIndexIfMissing` helpers to auto-migrate schema changes on every boot — new columns/indexes go there, not in a separate migration file.

**AI services** (`ai_services.js`): every feature is a chain that degrades to local logic, so the app works with zero keys configured. All of them are gated by a DB-backed toggle (`checkAIToggle`, `ai_settings`) and logged to `ai_logs`.

- **ID OCR** — `geminiIdScan` is the primary: it posts the image inline to Gemini (`GEMINI_OCR_MODEL`, pinned rather than a `-latest` alias) with a `responseSchema`, so the model returns `{name, idType, age, birthdate, gender, idNumber, address, text}` instead of prose that has to be pattern-matched. Falls back to `pytesseract_ocr.py` (local, offline), then NVIDIA Nemotron, then mock. It sits outside `callMockAI` because a multimodal request is a different shape from that helper's single fixed POST. The key travels in the `x-goog-api-key` header, never `?key=`, so it stays out of access logs.
- **The Gemini key is a list, not a value.** `GEMINI_API_KEY` plus `GEMINI_API_KEY_2`..`_5` (or one comma-separated `GEMINI_API_KEY`) are read by `geminiApiKeys()`, and `withGeminiKey()` tries them in turn, starting from whichever worked last. Only a refusal that names the *key* rotates — 429, or a 400/403 saying `RESOURCE_EXHAUSTED`/`API_KEY_INVALID`/quota/expired; a 500, a timeout or a schema mistake is reported to the caller instead, because retrying those across five keys just makes the desk wait five times as long and then reports a quota problem that does not exist. A free-tier key's per-day quota ends OCR until midnight Pacific, and the offline fallback reads a Philippine ID considerably worse, which is what makes the second key worth the machinery. Never log the key: the warning names the slot number. A 5xx is a third case: Gemini answers 503 "This model is currently experiencing high demand" under load, and a spare key cannot help with a busy model, so the *same* key is retried (`GEMINI_OVERLOAD_RETRIES`, default 2, backing off 700ms then 1400ms) before the request is handed back. Seen in production on the first live scan, where a single 503 dropped the desk straight to mock OCR. If a model *stays* busy the request moves to the next name in `geminiOcrModels()` (`GEMINI_OCR_MODEL_FALLBACK`, default `gemini-3.1-flash-lite`) rather than to the offline chain — an oversubscribed model stays that way for minutes, which the 2-second retry cannot outlast.
- **Both models default to `gemini-3.5-flash`, not the 3.6-flash Google names as the 2.5 replacement.** Measured on one ID photograph, one key, one schema: 3.6-flash 64.0s then 503; 3.5-flash 6.8s/8.4s; 3-flash-preview 9.1s/7.8s; 3.1-flash-lite 4.9s/6.3s; flash-lite-latest 1.8s/2.1s. All five transcribed the card correctly, so it is a latency choice, not an accuracy one — and 3.6 blew through the 30s request timeout, which is exactly how a live scan came back as "Detected Patient", age 29. Re-pin with `GEMINI_OCR_MODEL` if it settles.
- Both models are pinned in one place at the top of `ai_services.js` and default to `gemini-3.6-flash`. `GEMINI_CHAT_MODEL` exists because the Virtual Assistant's URL was hardcoded to `gemini-2.5-flash`, which Google now 404s as "no longer available to new users" — so on a recently issued key the VA failed *every* turn while OCR carried on working, and the key looked innocent because OCR proved it valid.
- **Report generation** — Hugging Face via `hfModel()`, which points at `router.huggingface.co/hf-inference/models` (`api-inference.huggingface.co` was retired and no longer resolves; the `hf-inference` provider segment is required, and a bare `/models/` path 404s).
- **The six analytics features** (anomaly, cutoff, estimation, performance, feedback, prediction) pass **no endpoint** and use their local logic directly. They previously posted queue figures to `distilbert-base-uncased`, a masked-language model that answers with fill-mask predictions; since a primary's response is returned *as* the feature's answer, a successful call was worse than a failed one — with a working endpoint, `/api/packages/estimate-time` returned `est_time_minutes: null` for every station. Putting a real model behind one of these means an endpoint whose response the caller can actually read.

`callMockAI(featureKey, endpoint, apiKey, data, firstFallback, mockFallback, featureLogName)` takes seven arguments and most call sites used to pass six, which put the log name in the `mockFallback` slot — hence `[AI Primary Failed] undefined:` in the terminal and `null` feature names in `ai_logs`. Count the arguments when adding a caller.

**Frontend** (`public/`): one HTML+JS pair per role (`frontdesk.html/js`, `laboratory.html/js`, `doctor.html/js`, `admintechnical.html/js`, `owner.html/js`, `customer.html/js`, plus landing `index.html/js`), no build step — pages are served statically and call `/api/*` directly with `fetch`. `shared.js`/`shared.css` hold cross-page utilities: token/role storage in `localStorage` (`clinicToken`, `clinicRole`, `clinicUsername`, `clinicCategory`), `authHeaders()`, `requireAuth(allowedRoles)` (redirects to `/index.html` if unauthorized), sidebar rendering, `logout()`, the promise-based `confirmAction()`/`promptReason()` dialogs (built from JS, since there is no templating to share markup through), `matchesSearch()`/`debounce()` for the search boxes, `initIdleTimeout()`, and the skeleton painters described below.

**Skeleton loading** (`shared.js` + the SKELETON LOADING block in `shared.css`): `skeletonTable`/`skeletonCards`/`skeletonStats`/`skeletonLines`/`skeletonValue` paint placeholder geometry for a section whose first fetch is in flight, and `clearSkeleton(...ids)` drops it plus the `aria-busy` flag. Two rules make them safe on these pages:

- A painter refuses to overwrite anything real (`skeletonSafe`), so the five-second queue poll on the station dashboards cannot flash placeholders over a list somebody is reading. Where the markup ships a static stand-in row ("No patients waiting in queue.") a first-load caller passes `replace: true`, and the station loaders additionally gate on `skeletonFirstLoad(key)`.
- The measurements come from the real CSS, not from numbers copied into the skeleton. `.skel-line` and friends are sized in `em`, so a placeholder dropped **inside** the real element (`<h3>`, `<div class="stat-value">`, a `<td>`) collapses to exactly one line box of that element. Build a new skeleton by reusing the real wrapper classes; guessing at generic bars measured 53px short per service card and 23px short per audit row. Block wrappers need `.skel-box` (`display: flow-root`) or the line's margins collapse out through them and the box comes up short.

**Rich text notepad** (`initRichTextEditor` / `richTextValue` / `setRichTextValue` in `shared.js`, `.rte*` in `shared.css`): the freeform result editor. Built by hand because this project has no bundler and loads no third-party scripts; formatting goes through `document.execCommand`, which is deprecated but is the only dependency-free way to format a selection. Two details are load-bearing: the toolbar acts on `mousedown` with `preventDefault` (a `click` would move focus out of the editable area first), and it only calls `focus()` when the caret is *not* already inside the box — focusing a contenteditable that already holds the selection collapses it in Chrome, so the command applies to nothing. Paste is forced to plain text.

`walkin-screen.js` is the Walk-in Intake screen, hosted by the front desk *and* both admin dashboards. It **builds its own markup** into an empty `<div id="section-walkin">` rather than having ~180 lines pasted into three HTML files — the two admin screens that were pasted into two files had already drifted apart before `admin-shared.js` consolidated them, and `shared.js` builds its dialogs from JS for the same reason. Its Advance/Hold buttons are enabled by `walkInCanAct()`, which mirrors `ROLE_STATION_TYPE` on the server: the front desk may move a walk-in standing at the front desk and nowhere else, while the elevated roles hold the override — which is the whole reason the screen is on the admin dashboards too. A button that cannot act says why in its tooltip instead of failing on click.

`admin-shared.js` holds the six screens `admintechnical.html` and `owner.html` both host — Manage Accounts, Manage Laboratories, Service Management, Medical Test Structures, Audit Log and Archives. Those existed as two near-identical copies that had already drifted apart; each page now keeps only its own sidebar, dashboard, and which roles it may create. It is loaded *after* `shared.js` and *before* the page script. `va.js` implements the customer-facing virtual assistant widget (speech recognition, VA state machine) that talks to `routes/assistant.js`.

**Real-time updates**: a single `socket.io` instance is created in `server.js` and attached to Express via `app.set('io', io)`; route handlers pull it from `req.app.get('io')` to emit events like `queueUpdate` after mutating queue state. Frontend pages listen for these to refresh live without polling.

## Conventions

- Uploaded ID images are deleted inside the request that reads them and never committed (`uploads/` is gitignored). Nothing about them is stored: `pending_registrations.front_id_path`/`back_id_path` are always written null - they used to hold real paths, but no screen ever displayed the images and the paths existed only so the files could be deleted later, which left a directory of identity documents waiting on a sweep that might not run. `ai_logs` is covered too: `logAI` redacts payloads for identity features (`IDENTITY_FEATURES` in `ai_services.js`), recording which fields a scan returned rather than what they said, so the extracted name, birth date, ID number and address do not land back on disk by another route.
- A visit enters the queue through `startPackageQueue()` in `queue_start.js` and nowhere else. A fourth intake route means another argument to it, not another copy of its inserts.
- A walk-in is a real customer row that cannot be signed in to. Anything that authenticates a user has to keep refusing `is_walk_in` accounts, and anything that lists customers should expect them: they have no email, no password anybody chose, and a `walkin-<id>` username.
- The printed intake form and the digital medical form ask the **same questions in the same words** (`WALKIN_HISTORY_CHECKLIST` / `WALKIN_HISTORY_QUESTIONS` in `walkin-forms.js` mirror `customer.html`). Changing one without the other breaks transcription, which is the only reason the paper form exists.
- Text bound for a PDF may only use glyphs jsPDF's built-in WinAnsi fonts actually have. `₱` is not one of them — it printed as `±450.00` next to a real amount — so `wfPeso()` writes `PHP 450.00`. `formatCurrency()` in `shared.js` keeps `₱`, because the browser has the glyph.
- `/api/display` is the only queue endpoint without an authenticated caller. It answers with ticket numbers and station names, never patient names, categories or service names — a waiting room full of strangers can read it.
- Ticket types are single-letter prefixes: `S` (Senior), `D` (PWD), `P` (Pregnant), `Q` (Regular). A ticket is minted once, at the front desk, and follows the patient for the whole visit — later stations reuse the same number rather than minting their own.
- Every service route starts *and* ends at the front desk, and only the front desk can declare a visit `completed` or `unfinished` (`POST /api/queue/finalize`). A laboratory or doctor can only hand the patient on. `/complete-step` refuses to close the final step and points at finalization instead.
- Soft deletion is the norm — go through `archiveRecord` in `archive.js` rather than writing `archived=true` by hand, so the snapshot, the label and the audit entry are always written together. Every archivable `entity_type` needs an entry in `ARCHIVE_TABLE_MAP` or it cannot be restored. `account_deletion_logs` and `archived_records` retain history for owner-facing audit trails.
- Any endpoint that changes clinic configuration or data takes a `reason` in its body and mounts `requireReason` from `audit.js`; the matching UI collects it with `promptReason()`. Adding a new configuration endpoint without both is a gap in the audit trail, not a shortcut. The deliberate exception is routine intake at the counter: `POST /api/walkin` audits every registration (who, when, which patient, which service) with a fixed reason rather than prompting, because asking a receptionist to justify each walk-in in prose with a patient standing in front of them produces "walk in" fifty times a day and no audit value. Writes that *configure* the clinic still prompt.
- The paused-patient state is called **On-Hold** (`queue.status = 'on-hold'`, `hold_reason`, `hold_at`, `POST /api/queue/hold` and `/resume`). It was previously "parked"; that spelling is gone from the schema, the API and the UI.
- New DB schema changes belong in `database.js`'s `initDB()` using `addColumnIfMissing`/`addIndexIfMissing`, so existing deployments auto-migrate on next boot.
- The shape of a medical test result is data, not code. A new test, a renamed parameter or a corrected reference range is an administrator's change under Medical Test Structures — not an edit to `public/laboratory.js`. A form with `input_mode = 'freeform'` deliberately has no fields: it hands the laboratory the notepad instead, which is what "Other Diagnostics" is.
- Rich text from the notepad is sanitised server-side in `POST /api/clinical-records` before it is stored, and again by `sanitizeRichHtml` wherever it is rendered. Adding another place that stores or renders it means routing through both.
- Agreeing to the Terms and Conditions happens in **step 1** of registration, before anything is submitted, and the Continue button is disabled until the box is ticked (`syncTermsGate` in `public/index.js`) with a validation backstop behind it. It used to sit in step 3 next to the OTP box, after the account details and the ID had already been sent.
- A section that fetches its own data shows a skeleton on first load, not a spinner or a stand-in figure - the markup used to ship `0`/`--`/"No patients waiting", which reads as an answer the page does not have yet. Reach for `showSectionLoader()` only for a genuine blocking overlay; it is no longer the default, and on the customer dashboard it was firing every five seconds over the patient's own ticket number.
